# Plan: Encrypt Private Keys at Rest

Status: implemented (2026-10-13), not yet released. See [Implementation notes](#implementation-notes) for details found while building it.

## Goal

Every private key the keystore writes to disk is encrypted. This cannot be turned off. Existing keystores upgrade in place: the plaintext keys they already hold are encrypted on first start of the new version, with no manual steps.

Decisions already made:

- The encryption key lives in **CertKit**, one per keystore. The keystore fetches it at startup and keeps it **in memory only**. It is never written to the keystore's disk.
- Deleting a keystore in CertKit destroys its key. That is accepted: the keys stored by that keystore become unreadable.
- If the storage folder holds keys encrypted with a different key (an earlier registration of this keystore), the keystore **starts over**: it moves the whole folder aside and begins with an empty one.
- The CA key and the server TLS key are encrypted too, not just customer certificate keys.
- `metadata.json` keeps only identifying fields (ID, thumbprints, serial number, issue date). No certificate PEM, chain or key.
- **File and folder permissions are unchanged.** A lockdown was built and then dropped as too likely to cause support calls (see [Security properties](#security-properties)).

## Background

What the code did before this change, and why each point matters:

1. **Private keys were plaintext PEM files**, in four places:
   - `<storage>/<customCertId>/<sha1>/key.pem`: the key for an issued certificate.
   - `<storage>/<customCertId>/csr/key.pem`: the key for a CSR waiting to be issued.
   - `<storage>/ca/ca-key.pem`: the keystore's CA key. Anyone holding it can create server certificates that agents trust for this keystore.
   - `<storage>/ca/server-key.pem`: the HTTPS server key.
2. **`metadata.json` held a second plaintext copy of the key.** `EnsureMetadata` saved the whole `api.IssuedCert`: the certificate PEM, the chain and, for keys that came from CertKit, the private key (`Key` at `api/poller.go:45` has no `omitempty`). Its only reader, `ReadLatestCert`, uses only `latestCert.sha1` to find the certificate's folder, where the same certificate, chain and key are already stored as separate files.
3. **On Windows, any local user can read the keystore's files.** `C:\ProgramData\CertKit` lets `BUILTIN\Users:(RX)` read its contents, and Go's `0o600` has no effect on Windows. That includes `config.json`, which holds the keystore's ed25519 auth key. This change leaves that as it is.
4. **Serving agents already depends on CertKit.** Every agent request calls CertKit's `validate-agent-request` (`server/handlers.go`). So making the keystore fetch its key from CertKit at startup doesn't make serving any less available.
5. **The frontend already encrypts keys in its database.** `ColumnEncryptor` uses AES-256-GCM with a random 12-byte nonce, a key ID ("kid") and AAD, storing `*_enc`, `*_nonce` and `*_kid` columns. The keystore's at-rest format follows the same approach.
6. **Agents trust the keystore through the CA certificate stored on the CertKit record** (`keystore.CaCertificate`, `AgentApiController.cs:504`). `EnsureCA` only sends it to CertKit when it creates a CA.

## Design overview

```
              register (unchanged)
 keystore ───────────────────────────────▶ CertKit
    │
    │  startup: POST /api/keystore/v1/{id}/encryption-key
    │  (signed request; retried until it succeeds)
    │◀──────────────── { "key": "<base64, 32 bytes>" }
    │                     (created on the first request, never changed after)
    ▼
 key held in memory ──▶ encrypt/decrypt key.pem, ca-key.pem, server-key.pem
```

- **Cipher:** AES-256-GCM, Go standard library only.
- **Key:** 32 random bytes generated by CertKit and stored encrypted with `ColumnEncryptor` on the `keystores` row.
- **File format:** the files keep their names. The contents become a PEM block of type `CERTKIT ENCRYPTED PRIVATE KEY`.
- **Old files:** the keystore checks the PEM block type when reading. Plaintext keys are still accepted, and the startup migration encrypts them.

### Why a separate endpoint and not poll

- **Poll returns 403 until the keystore is approved**, but a new keystore needs its key immediately, because it creates its CA key and starts HTTPS before approval.
- **The key is needed once per process start.** It belongs before the CA and TLS setup, not in a poll response every 30 seconds.

### Why create the key on first request, not at registration

Existing keystores are already registered, so they need the "create if missing" path no matter what. A single get-or-create function covers new installs and upgrades alike, and registration doesn't change.

## Encrypted file format

```
-----BEGIN CERTKIT ENCRYPTED PRIVATE KEY-----
Kid: 3f9a12c0

<base64( nonce[12] || ciphertext || tag[16] )>
-----END CERTKIT ENCRYPTED PRIVATE KEY-----
```

- **Kid:** the first 4 bytes of SHA-256(key), in hex. The keystore works it out from the key. It is unrelated to `ColumnEncryptor`'s kid column. It lets the keystore tell "encrypted with a different key" apart from "corrupt".
- **AAD:** the Kid value, so changing the header makes decryption fail.
- **Plaintext:** the original PEM bytes, unchanged.
- **Reading by block type:**
  - `CERTKIT ENCRYPTED PRIVATE KEY`: check the kid, then decrypt.
  - `PRIVATE KEY`, `EC PRIVATE KEY` or `RSA PRIVATE KEY`: an older plaintext file, returned unchanged.
  - Anything else is an error.
- **Why the filenames stay the same:** paths, `IsKeyOnDisk`, the folder layout and `HasPendingCSR` don't change, and the migration can replace each file in a crash-safe way.

## Frontend changes (`c:\source\certkit\Frontend\src\CertkitFrontend`)

### Schema

- **New migration file** `SQL/alter-2026-10-13-keystore-encryption-key.sql` (plus `SQL/init.sql`), adding to `keystores`:
  ```sql
  ALTER TABLE keystores ADD COLUMN encryption_key_enc   BLOB;
  ALTER TABLE keystores ADD COLUMN encryption_key_nonce BLOB;
  ALTER TABLE keystores ADD COLUMN encryption_key_kid   TEXT;
  ```
- **No backfill.** Keys are created on first request.
- **Applied by hand.** There is no migration runner.

### `Keystores/KeystoreService.cs`

**`GetOrCreateEncryptionKey(int keystoreId)`** returns the base64 key.
- **If the row already has a key:** decrypt it with `ColumnEncryptor.Decrypt(enc, nonce, aad, kid)` and return it. If it can't be decrypted, throw; never create a replacement.
- **Otherwise:**
  1. Generate a key with `RandomNumberGenerator.GetBytes(32)`, convert it to base64, and encrypt it with `ColumnEncryptor.Encrypt(base64Key, aad)`.
  2. Save it with `UPDATE keystores SET encryption_key_enc = @Enc, encryption_key_nonce = @Nonce, encryption_key_kid = @Kid WHERE id = @Id AND encryption_key_enc IS NULL`.
  3. Read the row back and decrypt it. If two first requests arrive at once, one write wins and both return the winning key.
- **AAD:** `keystore_encryption_key_{keystoreId}`, in the same style as `Certificate.PrivateKeyPemAad`.
- **The encrypted columns are read by their own query**, so they never reach the `Keystore` model or its `SELECT *` queries.
- **When a key is created**, log a `KeystoreLogService` event (`EVENT_ENCRYPTION_KEY_CREATED`) saying "Encryption key created." Only the request whose write landed logs it.

### `Controllers/KeystoreApiController.cs`

New endpoint:

```
POST /api/keystore/v1/{keystoreSqid}/encryption-key      [AuthorizeKeystore]
request:  {}
response: { "key": "<base64, 32 bytes>" }
```

- **Lookup checks:** the same not-found checks as the other endpoints (`KeystoreIdMapper.FromSqid`, `GetKeystoreById`).
- **No approval check**, the same as `update-ca-info` and `log`. The key protects only what this keystore writes itself, so an unapproved keystore has nothing to protect yet, and a new keystore needs the key before approval to create its CA.
- **Encoding:** `Convert.ToBase64String` (standard, padded); the keystore decodes it with `base64.StdEncoding`.
- **No caching:** `Cache-Control: no-store`.
- **Never log the key.**

### Delete warning

There is no separate delete-keystore screen. `KeystoreService.DeleteKeystore` has no callers; a keystore is only deleted when its collection is deleted, through the foreign-key cascade. The admin "Delete collection" confirmation (`Pages/Admin/AdminCustomerDetails.cshtml`) shows this warning when the collection has a keystore:

> Are you sure you want to delete this collection? Deleting it also deletes its keystore and permanently destroys the keystore's encryption key. Private keys stored on the keystore server can no longer be read, including keys it generated for certificate requests. Those certificates will need to be reissued.

Two other paths cascade without a warning: the admin delete-customer modal and `TrialAccountCloserJob`.

## Keystore changes (this repo)

### New code

| File | Contents |
|---|---|
| `crypto/atrest.go` | `EncryptedKeyPEMType` and `EncryptionKeySize` consts; `ErrKeyMismatch`; `KeyID(key) string`; `EncryptPrivateKeyPEM(key, plaintextPEM)` (refuses anything that isn't a plaintext private key PEM, including already-encrypted data); `DecryptPrivateKeyPEM(key, data)` (returns plaintext files unchanged; `ErrKeyMismatch` when the kid differs); `EncryptedKeyID(data) (kid, encrypted)` |

| `storage/encryption.go` | Key held in a package variable, set once at startup before any goroutine reads it. `SetEncryptionKey`, `WritePrivateKey(path, pem)`, `ReadPrivateKey(path)`, `CheckPrivateKey(path)`, `StartOverIfUnreadable()`, `MigrateToEncrypted() MigrationResult`, and `writeFileAtomic(path, data)`, which writes a temp file in the same folder, flushes it to disk, closes it, then renames it over the target. `WritePrivateKey` returns an error if no key is set: plaintext is never written. |

### metadata.json format

```go
// CertInfo identifies the latest issued cert. The PEMs live in the cert's
// SHA1 directory; nothing secret is stored here.
type CertInfo struct {
	Id           int       `json:"id"`
	SHA1         string    `json:"sha1"`
	SHA256       string    `json:"sha256"`
	SerialNumber string    `json:"serialNumber"`
	IssueDate    time.Time `json:"issueDate"`
}

type CertMetadata struct {
	LatestCert *CertInfo `json:"latestCert"`
}
```

**The JSON field names don't change.** New code reads old files, because Go ignores the extra `pem`, `chain` and `key` fields. Older binaries read new files too, since they only need `sha1`.

### Startup sequence (`cmd/certkit-keystore/run_common.go`)

```
LoadConfig                          (existing)
register if needed                  (existing)
waitForEncryptionKey(stopCh)        NEW: return if stopCh closes
storage.SetEncryptionKey            NEW
storage.StartOverIfUnreadable       NEW: exits (and the service restarts) if the move fails
storage.MigrateToEncrypted          NEW: save the result to report later
EnsureCA                            (existing)
NewTLSManager                       (existing)
runStartupChecks                    (existing; now also reports starting over and migration results)
start HTTPS server + poll loop      (existing)
```

**`waitForEncryptionKey`**
- Calls `api.FetchEncryptionKey()` and retries with backoff: 5s, 10s, 20s, 40s, then every 60s.
- Logs each failure locally ("Waiting for encryption key from CertKit: … retrying in Ns").
- Each wait also listens on `stopCh`, so a service stop or SIGTERM still works.
- On Windows the service reports Running before `runKeystore` starts (`run_windows.go:66-71`), so waiting here doesn't hit the service start timeout.

**Reporting in `runStartupChecks`** (sent to CertKit with `LogKeystoreEvent`):
- If the storage folder was moved aside: "Stored private keys were encrypted by an earlier registration of this keystore and cannot be read. Moved the storage directory to … and started over. Keys CertKit holds will be downloaded again; certificates that used keystore-generated CSRs must be reissued." (error)
- If N > 0: "Encrypted N existing private key(s) at rest." (info)
- If F > 0: "Failed to encrypt F private key file(s) at rest: …" (error)

## Upgrade and migration

### Starting over

`StartOverIfUnreadable` runs at every startup, right after the key is set.

1. Look at every key file (the same list the migration uses, below).
2. If any is encrypted with a kid other than the current key's, rename the whole storage folder to `<storage>.unreadable-<UTC timestamp>` and carry on with an empty folder.

**When this happens:** the folder was used by an earlier registration of this keystore. That registration's key was destroyed with it in CertKit, so nothing in the folder can be read. The usual way to get here is to uninstall, register a new keystore, and keep the default storage path.

**Why start over rather than repair file by file:**
- Without it, the keystore can't start. `EnsureCA` would find the old CA, the HTTPS setup couldn't decrypt the CA or server key, and the process would exit and restart forever. It would never reach the poll loop.
- A new registration needs a new CA anyway: its CertKit record has no CA certificate until `EnsureCA` creates one and sends it.
- After starting over, CertKit re-sends the keys it holds on the next poll. Certificates that used keystore-generated CSRs show `KeyNotFound` and must be reissued.

The old folder is moved, not deleted. **If the rename fails** (the storage folder is a drive root or mount point, or a file inside it is open), the keystore exits with the error and the service manager restarts it, which retries the move.

### Encrypting existing keys

`MigrateToEncrypted` runs next, at every startup. It is safe to run repeatedly, cheap, and never stops partway because one file failed.

1. **Find key files:**
   - `<storage>/*/*/key.pem` (both the `<sha1>/` and `csr/` folders).
   - `<storage>/ca/ca-key.pem` and `<storage>/ca/server-key.pem`.
2. **Handle each file:**
   - **Already encrypted:** skip it.
   - **Plaintext:** encrypt it, decrypt the result and compare it with the original, then `writeFileAtomic` it over the original. Count it as N.
   - **Any error:** log it, count it as F, and continue.
3. **Clean up metadata:** for each `<storage>/*/metadata.json`, parse it into the slim `CertMetadata` and serialize it again. If the result differs from the file, rewrite it with `writeFileAtomic`. This also covers certificates that no longer appear in poll, which `EnsureMetadata` would never touch.
4. **Return** N and the failures, which `runStartupChecks` reports.

**Crash safety:** reads accept both formats, and each file is replaced in one atomic rename. A crash at any point leaves a usable store, and the next startup finishes the job.

**Downgrades are not supported.** An older keystore would hand agents an encrypted file they can't read, and would fail to load the encrypted CA key. Updates only move forward, so that's acceptable.

## Edge cases

| Situation | Behavior |
|---|---|
| CertKit unreachable at startup | The keystore waits and logs locally until CertKit answers. Agents couldn't be served during that time anyway. |
| Keystore deleted in CertKit | The key is destroyed. A keystore still running keeps its key in memory until it restarts. After a restart it can't fetch the key, keeps retrying and logs locally. Its stored data can no longer be read, which is intended. |
| Uninstall, then reinstall as a new keystore over the same storage folder | The storage folder is moved aside and the keystore starts over (see [Starting over](#starting-over)). |
| A single `key.pem` from another keystore copied into the folder | The whole folder is moved aside. Moving it back and deleting the stray file restores it. |
| A plaintext `key.pem` dropped onto disk | Accepted when read, and encrypted at the next startup |
| Storage folder can't be renamed | The keystore exits with the error; the service manager restarts it and it tries again |
| Startup wait vs. service stop | The wait listens on `stopCh`, so it exits cleanly |

## Release order

**The frontend ships first.** An upgraded keystore waits at startup until the `encryption-key` endpoint answers. If a keystore upgraded itself before the endpoint was live, it would retry forever and serve nothing.

1. Frontend: run `SQL/alter-2026-10-13-keystore-encryption-key.sql` against production `/data/app.db`, then deploy the schema, `GetOrCreateEncryptionKey`, the endpoint and the delete warning.
2. Keystore: release.

## Security properties

**Protects against:**
- A copy or backup of the storage folder alone: there is no key on disk.
- Storage on a network share or a separate volume.
- Stray or leaked `key.pem` files.
- Lost or stolen copies of the data, as long as the keystore is deleted in CertKit, which destroys the key centrally.

**Does not protect against:**
- An administrator (root or SYSTEM) on the machine. They can read process memory, or use `config.json` to fetch the key.
- Anyone who can read `config.json` while the keystore exists in CertKit. Its ed25519 auth key can sign the request that fetches the encryption key. On Linux, `config.json` is `0600` and owned by root. **On Windows, with permissions unchanged, any local user can read it**, so local non-admin users on a Windows keystore are not kept out of the keys.
- A full copy of the disk while the keystore still exists in CertKit, for the same reason.

## Implementation notes

- **Redacted keys are refused.** If CertKit can't decrypt a certificate's key, poll sends a `-----BEGIN REDACTED PRIVATE KEY-----` placeholder. Older versions stored it as `key.pem`. Now `WritePrivateKey` refuses it, and the certificate reports `CertNotStored` instead of a misleading Synced. An existing redacted `key.pem` counts as a migration failure (F) each startup until someone deletes it.
- **Test hooks:** `server.updateCAInfo`, `fetchEncryptionKey` and `encryptionKeyRetryDelays` are package variables so tests can replace them.
- **Frontend endpoint tests:** there's no in-process HTTP test harness, so "works for an unapproved keystore" and "rejects an unsigned request" aren't tested automatically.
- **Permissions lockdown dropped.** It was built (protected Windows ACLs on the config and storage folders, `0700` on Linux) and then removed before release.
- **Not verified automatically:** a full run of a keystore against a frontend that has the new endpoint.

## Out of scope / future

- **Key rotation.** The Kid header leaves room for it. It would need CertKit to hold several keys and the keystore to re-encrypt files.
- **Restricting who can read `config.json` on Windows**, or tying it to the machine (Windows DPAPI, systemd-creds/TPM), so it can't be used elsewhere to fetch the key.
- **Extra checks on the encryption-key endpoint**, such as source-IP or machine-ID checks.
- **Public docs** (`CertKitOther/documentation`): describe encryption at rest and what deleting a keystore does.
